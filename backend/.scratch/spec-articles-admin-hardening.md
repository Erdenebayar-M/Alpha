# Spec: Articles admin API — race-safety, round-trip and duplication fixes

## Problem Statement

Two `/code-review` passes over the Articles admin backend (issues #80/#81, #82, #83, #84, #85, #86 — commits `f2935d7`..`026763b`) turned up nine problems in `backend/src/routes/adminArticles.ts` and `shared/src/validators/article.ts`. None of these are visible in the happy path the existing 128 tests cover; they surface under concurrent admin actions, when a Published Article is re-saved, or when a video Block is round-tripped through the editor. Left as-is:

- A staff member can silently lose the site's Featured article by clicking Feature at the wrong moment.
- A staff member can accidentally delete an Article moments after a colleague publishes it.
- A staff member can save a live, Published Article into a state that fails the site's own publish requirements (no thumbnail, no excerpt, empty body) with no warning.
- A staff member cannot re-save an Article that contains a video Block without the client reconstructing a pasted URL from stored data — the editor's own read/write round-trip is broken.
- Two staff members racing to feature different Articles at the same time get an unhandled 500 instead of a clear outcome.
- Several of these races surface as an unhandled 500 (an unguarded `.update()`, or a `decorateArticle(x!)` non-null assertion on a row that can legitimately be gone) instead of a proper `NOT_FOUND` or no-op.
- The not-found lookup and the write-then-refetch-and-respond pattern are each hand-copied five times across the file, in violation of this repo's `CLAUDE.md` de-duplication rule, which means the null-race bug had to be (and wasn't) fixed in five places at once.

## Solution

Harden the existing Articles admin route handlers so every write is race-safe under concurrent admin actions, every "row disappeared mid-request" case degrades to a clean response instead of a 500, a Published Article can't be silently un-published-in-substance via `PUT`, and a video Block survives a read/save round-trip. Extract the two duplicated request-handling shapes (lookup-or-404, and write-then-refetch-and-respond) into shared helpers within the route module so the fix lives in one place and future routes inherit it for free.

No new HTTP endpoints, no schema changes, no new admin-facing behavior beyond the video Block fix and the Published-article guard on `PUT`. This is a hardening pass on work already shipped, not a new feature.

## User Stories

1. As a staff editor, I want unfeaturing an Article to never throw a server error even if another editor deleted or unpublished it moments earlier, so that I'm not blocked by a race I can't see.
2. As a staff editor, I want featuring an Article to never leave the site with zero Featured Articles because of a concurrent unpublish, so that the site's Featured slot doesn't silently go empty without anyone choosing that.
3. As a staff editor, I want to load a Published Article, save it back unchanged, and have it stay valid for publication, so that routine re-saves can't accidentally break the live site.
4. As a staff editor, I want to add a YouTube or Vimeo video Block, save the Article, reload it, and save it again without the video Block being rejected, so that the editor's own round-trip doesn't lose or invalidate my content.
5. As a staff editor, I want deleting a Draft to fail cleanly if a colleague published it a moment before my delete lands, so that a just-published, shared-link Article is never silently destroyed.
6. As a staff editor, I want any admin Articles action on a row that's already gone (deleted by someone else mid-request) to return `NOT_FOUND`, never an unhandled 500.
7. As two staff editors acting at the same moment (one featuring Article A, one featuring Article B), I want each request to resolve to a clear, correct outcome — not an opaque 500 from a database constraint neither of us can see.
8. As the developer maintaining this file, I want the "look up the Article or return NOT_FOUND" and "write, then refetch and return the decorated Article" shapes each written once, so a future correctness fix (or a future route) doesn't require hand-copying it a sixth time.
9. As a staff editor, I want unfeaturing an Article to make one database write instead of two round trips for the same logical change, so admin actions stay fast under load.
10. As a staff editor, I want these fixes to change nothing about the currently-passing behavior (the 128 existing tests, the response envelope, the error codes, the `was_published` derivation, ADR 0002's one-hand-picked-Featured rule) so my existing workflows keep working exactly as they do today.

## Implementation Decisions

**Seam:** all changes are made and tested at the existing HTTP route seam (`adminArticles.request(...)` against the Hono sub-app, exactly as the current 1307-line `admin-articles.test.ts` already does, with `prisma.article.*` mocked). No new seam is introduced. The video Block fix touches `shared/src/validators/article.ts` but is exercised end-to-end through the same route seam (via `saveArticleSchema`/`createArticleSchema`), matching how every other Block kind is already tested — no standalone shared-package test file is added.

- **Shared helper: `findArticleOrNotFound`.** Replaces the five copies of `findUnique(... select: ARTICLE_SELECT) → if (!article) return NOT_FOUND`. Returns either the article row or has already written the `NOT_FOUND` response and signaled the caller to return early (the existing repo convention for this — e.g. a discriminated result or a thrown sentinel the route can check — should follow whatever pattern reads cleanest against Hono's `Context`; this is an implementation-time choice, not a locked interface).
- **Shared helper: refetch-and-respond.** Replaces the five copies of `findUnique(...) → ok(c, { article: decorateArticle(x!) })`. Takes the article id, re-reads with `ARTICLE_SELECT`, and returns the `ok(c, ...)` envelope — but **must not** use a non-null assertion: if the refetch returns `null` (the row was deleted between this handler's write and its refetch), it returns `NOT_FOUND` instead of throwing. This single change fixes finding 6 (`decorateArticle(article!)` crash) everywhere it currently occurs (`PUT`, `publish`, `unpublish`, `feature`, `unfeature`).
- **`feature` transaction — don't silently drop the Featured flag on a no-op set.** When the transaction's second `updateMany` (the one that sets `is_featured: true` on the target id, guarded on `status: 'PUBLISHED'`) matches zero rows, the transaction must not commit the first `updateMany` (the one that cleared every other Article's Featured flag). Throw inside the transaction callback when the second step's `count` is 0 so Prisma rolls back both steps together; the route then returns the existing `UNPROCESSABLE` response for "Only Published Articles can be Featured" as it does today.
- **`feature` — two concurrent Feature calls must not 500.** The unique index that enforces "at most one Featured Article" (ADR 0002) can still be hit if two transactions interleave. Catch the resulting unique-constraint error from the transaction and translate it into a clean, already-defined error response (the existing `UNPROCESSABLE` "Only Published Articles can be Featured" is acceptable, or a `CONFLICT` if that reads better against `src/lib/errors.ts`'s existing vocabulary) rather than letting it propagate to `app.onError`.
- **`unfeature` — race-safe write, one round trip.** Replace the bare `prisma.article.update({ where: { id }, data: { is_featured: false } })` with the same guarded `updateMany`-then-check-count pattern `publish`/`unpublish` already use (guard on `id` — `is_featured: true` is optional extra safety, since the point is just "don't throw if the row is gone"), and use the write's own returned/refetched data instead of issuing a second `findUnique` for the same row. If it becomes the shared refetch-and-respond helper's job to do the one necessary read, `unfeature` should call that helper rather than reading twice.
- **`DELETE /:id` — guard the delete on status, not just id.** Change `prisma.article.delete({ where: { id } })` to the guarded-delete pattern already used by `publish`/`unpublish` for updates: `prisma.article.deleteMany({ where: { id, status: 'DRAFT' } })`, and treat a `count` of 0 as either `NOT_FOUND` (row is gone) or the existing `UNPROCESSABLE` "Published Articles must be unpublished before they can be deleted" (row exists but is now Published) — distinguish the two with a cheap follow-up read the same way `PUT` already does for its own zero-count case, or by checking existence first inside the same request. This closes the window where a concurrent Publish lands between the initial status read and the delete.
- **`PUT /:id` — a Published Article can't be saved into a Publish-invalid state.** When the Article being saved is currently `status: 'PUBLISHED'`, run the same `getArticlePublishIssues` check `POST /:id/publish` already runs, against the *incoming* save payload, before writing. If any required field would be missing (title, slug, excerpt, thumbnail, non-empty body), reject with the same `UNPROCESSABLE` shape `publish` uses (`{ missing: [...] }`) instead of writing. A Draft being saved is unaffected — this check only applies when the row's current status is `PUBLISHED`.
- **`shared/src/validators/article.ts` — `videoBlockSchema` accepts its own stored shape.** Currently the schema only accepts `{ id, type: 'video', url }` (a pasted URL, parsed server-side into `{ provider, video_id }` for storage) and rejects the `{ id, type: 'video', provider, video_id }` shape the API itself returns from `GET`/`POST`/`PUT`. Extend the schema to accept *either* input: a pasted `url` (parsed exactly as today, for a newly-added video Block), *or* an already-valid `{ provider, video_id }` pair (passed through unchanged, for an untouched video Block being re-saved as part of a larger edit). Storage and the response shape are unchanged — this is purely an input-acceptance fix so the editor's own GET→PUT round-trip stops failing validation.

## Testing Decisions

- Follow the existing structure and helpers in `backend/src/routes/__tests__/admin-articles.test.ts` exactly: the same `prisma.article.*` jest mocks, the same `createArticle`/`saveArticle`/`publishArticle`/`unpublishArticle`/`deleteArticle`/`featureArticle`/`unfeatureArticle` request helpers, the same `ok`/error-envelope assertions. New `describe` blocks should sit alongside the existing per-route blocks (`describe('PUT /:id', ...)`, `describe('DELETE /:id', ...)`, `describe('POST /:id/feature', ...)`, `describe('DELETE /:id/feature', ...)`).
- Test only externally observable behavior: HTTP status, response envelope shape (`success`/`data`/`error.code`), and which `prisma.article.*` methods were called with which `where`/`data` — never internal helper names or control flow. The extraction of `findArticleOrNotFound` / refetch-and-respond is an internal refactor; no test should assert on the helpers' existence, only on the routes' observable behavior before and after.
- Race conditions are simulated the way the current suite already does elsewhere in this file: by mocking a `prisma.article.*` call to return `count: 0` / `null` on a specific invocation (via `mockResolvedValueOnce` / `mockImplementationOnce`) to stand in for "another request already changed this row," not by spinning up real concurrency.
- Cover, per finding: (1) feature-transaction rollback when the second step matches zero rows — assert the first `updateMany` (clear-all) is not observably committed, i.e. the transaction fn throws and no `ok` response with a cleared Featured flag is returned; (2) two-request feature collision — mock the transaction to throw the unique-constraint shape and assert a clean 4xx, not a 500; (3) `unfeature` on an already-gone row — mock the guard write to affect zero rows and assert `NOT_FOUND`, not a thrown error, and assert only one `prisma.article.*` read/write pair fires; (4) `DELETE /:id` racing a concurrent publish — mock the guarded delete to affect zero rows with the row now `PUBLISHED`, assert the existing "must be unpublished before delete" `UNPROCESSABLE`; (5) `PUT /:id` on a Published Article with a blanked thumbnail/excerpt/body — assert `UNPROCESSABLE` with `missing` naming the right fields, and assert no write was attempted; (6) `PUT /:id` and `POST /` each accepting a video Block payload shaped as `{ id, type: 'video', provider: 'youtube', video_id: '...' }` (no `url`) as well as the existing `{ url }` form; (7) every route already covered for the null-refetch crash (`PUT`, `publish`, `unpublish`, `feature`, `unfeature`) gets one test where the post-write refetch returns `null` and the response is `NOT_FOUND`, not a thrown `TypeError`.
- Baseline: `npm run test:backend` must stay green throughout — the existing 128 Articles tests are the regression guard that these fixes must not change any currently-correct behavior.

## Out of Scope

- Any change to the public read API (`backend/src/routes/articles.ts`) — none of the nine findings touch it.
- Any change to `POST /api/admin/articles/images` (upload endpoint) — not implicated.
- Redis-backed or any other cross-request locking mechanism — every fix here uses the same guarded-`updateMany`/transaction-rollback pattern the codebase already established for `publish`/`unpublish`, not a new concurrency primitive.
- Changing what fields `getArticlePublishIssues` checks, or the 38 error-code catalogue, or `ERRORS.*` — the `PUT`-on-Published guard reuses the existing readiness check and existing `UNPROCESSABLE` error verbatim.
- Reworking `videoBlockSchema`'s URL-parsing logic (YouTube/Vimeo id extraction) — only the accepted *input shape* changes; parsing behavior for a pasted URL is unchanged.
- Any admin UI/frontend work — this is backend-only, matching how #81–#86 shipped.
- Renaming or restructuring `adminArticles.ts` beyond extracting the two named helpers — no broader file reorganization.
